NFL MEDICAL DATA PLATFORM: LOCAL PIPELINE TEST HARNESS
(Plain-language twin of README.md. Both are updated together.)

WHAT IT IS
A set of Docker containers on your own computer that pretends to be a healthcare-style reporting pipeline. Data starts in a MySQL database, is copied into PostgreSQL, loaded into a reporting schema, written out as Parquet files to S3-style storage, turned into a report with a checksum, and delivered over SFTP. Airflow runs the middle steps. A collection of Bruno API requests checks every stage, and a second set of requests breaks things on purpose to prove the problems are noticed and an alert is sent. All the data is made up; it is generated by infra/sql/04-seed.sql.

WHAT IT IS NOT
It tests the pipeline's contract before anything is built in AWS. It is not the production pipeline, and a green run does not prove an AWS deployment works. Debezium stands in for AWS DMS, Python and SQL inside Airflow tasks stand in for Apache Hop and Spark, and a local mail server stands in for the real alert channel. There is no dashboard. docs/COVERAGE.md says, requirement by requirement, what is and is not proven.

WHAT YOU MUST SUPPLY
floci, a local AWS emulator, has to already be running on port 4566. This project does not start it.

WHAT YOU NEED
Docker with compose v2 or later, python3, curl, lsof and ssh-keygen, and the bru command (npm install -g @usebruno/cli) to run the Bruno requests from a terminal. These ports must be free, all on 127.0.0.1 only: 3307, 5440, 8094, 8095, 8096, 8097, 8098, 9099 and 2225. You do not need Java, Maven or a database client. The scripts are bash; they are written for macOS and Linux.

HOW TO RUN IT
1. Check floci answers: curl -fsS http://localhost:4566/_localstack/health
2. Generate secrets and SFTP keys, once: scripts/init-env.sh (it will not overwrite an existing file).
3. Start everything: scripts/up.sh. When it exits 0 and prints "Stack is up", all 12 containers are healthy and every check login worked. Cold, that takes about 100 seconds.
4. Run the checks: go into the bruno folder, load the secrets into your shell with set -a; . ../infra/nfl.env; set +a, then run bru run -r --exclude-tags chaos --env local with two extra options, --env-var "airflow_password=${AIRFLOW_ADMIN_PASSWORD}" and --env-var "aws_secret_access_key=${AWS_SECRET_ACCESS_KEY}".
5. Optional, after a green run: the same command with 90-chaos instead of -r --exclude-tags chaos, which breaks ten things one at a time and checks each is noticed, alerted and restored.
6. Stop with scripts/down.sh (keeps data) or wipe with scripts/reset.sh -y.
Never start the stack with a plain docker compose up. It skips the env file, the storage bucket, the database permissions and the connectors.

IF SOMETHING GOES WRONG
up.sh stops and names the port or tool that is the problem. Ports can be changed in infra/nfl.env (the template is infra/env.example.txt). For failures during startup read section 5 of docs/RUNBOOK.md. FROM-NOTHING.txt walks through every command with an explanation.

WHAT YOU CAN LOOK AT
http://localhost:8094 is the inbox of every alert email. http://localhost:8095 is the Airflow screen (user nfladmin, password AIRFLOW_ADMIN_PASSWORD in infra/nfl.env). curl localhost:8096/checks lists every read-only check. Seeded bad rows (missing and duplicate keys, an orphan transaction), tagged BAD-1 to BAD-7 in the seed file, are there on purpose so the quality gate has something to reject. The last recorded Bruno results, from 2026-10-07 and not re-run when this file was written, were 109 requests and 344 tests for the normal run, and 86 requests and 233 tests for the chaos run.

THE SERVICES
The shim on port 8096 answers read-only checks over HTTP, each connecting to its backend as its own limited identity. The DMS stub on 8098 answers in the shape of the AWS DMS API, with its status taken from the real Debezium connector. Airflow is on 8095 with a login. Kafka Connect is on 8097, the mail inbox on 8094. MySQL, Postgres, Kafka and SFTP are on 3307, 5440, 9099 and 2225 with generated passwords.

TESTS
Without the full stack, and run on every pull request by GitHub Actions: all Python files compile; docs/check_coverage.py --check confirms the coverage document recounts correctly and every Bruno file and Airflow task it cites exists; the compose file validates against the committed template; the DMS stub self-test passes (78 checks, 0 failures). A separate job scans the whole git history for secrets with gitleaks. The Bruno end-to-end collection needs the full stack and floci, so it is not run in GitHub Actions. It was not re-run in the 2026-11-18 cleanup either, because floci was not available.

WHERE THINGS ARE
scripts holds the start, stop and wipe scripts. infra holds the compose file, Airflow DAGs, SQL, MySQL and Debezium config. shim, stub and watch are the three small Python services. bruno is the request collection. docs holds ARCHITECTURE.md, COVERAGE.md, DECISIONS.md and RUNBOOK.md. WHAT-DOES-WHAT.txt and FROM-NOTHING.txt are the plain guides.

DESIGN CHOICES WORTH KNOWING
Debezium does the real change capture and only the DMS control plane is faked, because floci does not implement DMS and a fully faked one would prove nothing about replication. The secrets file is infra/nfl.env and not .env, because the maintainer's tooling blocks every .env path; as a result every script names the file explicitly. Each shim check uses its own database login so no check can read more than it reports. The watcher is its own container, not an Airflow job, because Airflow is one of the things it watches. All ports bind to 127.0.0.1 only.
