THE PIPELINE IN ONE BREATH
MySQL (the source) -> Debezium copies changes -> Postgres staging -> ingestion loads staging into utm ->
extraction writes Parquet to S3 -> reporting builds a CSV report -> delivery uploads it to SFTP.
Airflow runs the three middle steps. A watcher looks at the whole thing on a timer and emails alerts.
A check shim and a Bruno collection let you ask any of it a question over HTTP.

Stand-ins, so nobody is misled: Debezium stands in for AWS DMS, Python/SQL inside Airflow stands in for
Apache Hop and Spark, floci stands in for AWS (S3 and CloudWatch Logs), a local mail server stands in for
the Operations alert channel. The contract between stages is real; those engines are not.

6. OBJECT STORE AND LOG STORE: floci, port 4566 (NOT part of this project; nothing here starts it)
  What it does   Pretends to be AWS. The stack uses its S3 (Parquet, manifest, marker, reports) and its
                 CloudWatch Logs (shipped logs under /nfl/).
  Know this      It accepts any access key and enforces no permissions. Its log filter is a plain substring
                 match and it answers 200 for a log group that does not exist. Real AWS does none of that.

8. THE WATCHER: container nfl-watch, no host port
  What it does   Every 15 seconds, without being asked: measures the replication heartbeat, both connectors
                 and Airflow's health, saves each measurement, raises an alert when one goes bad and a
                 recovery when it comes back. It also emails every alert, its own and the DAGs', and records
                 each attempt. It is not an Airflow DAG because Airflow is one of the things it watches.
  Code           infra/docker-compose.yml:550, watch/app.py

                 :256  settle               decides the level; a probe that cannot run 3 times becomes critical
                 :274  record               saves the sample, writes the alert or recovery on a change
                 :353  compose              builds the alert email

14. ONE ID THROUGH EVERYTHING: the correlation id
  What it does   The caller passes conf.correlation_id to each of the three triggers. Every event row, every
                 task log and every alert email carries it, so one id finds everything about one attempt.
                 A run triggered without one uses nfl_<start>_<end>. A watcher incident uses
                 nfl_watch_<probe>_<epoch> for its alert and its recovery.
  Code           infra/airflow/dags/nfl_common.py:136, infra/sql/05-observability.sql:53
  Ask it         curl -s 'localhost:8096/checks/trace?correlation_id=<id>'


15. AN ALERT, START TO FINISH
  1. A task uses its last retry, or the watcher sees a probe go bad.
  2. A row is written to observability.pipeline_event with alert = true, a severity (critical, warning or
     info), the error summary and the log links.
     infra/airflow/dags/nfl_common.py:333 or watch/app.py:274
  3. Within one tick the watcher emails it and records the attempt.   watch/app.py:401
  4. It is in the inbox (http://localhost:8094) and on /checks/alerts/delivery as "sent".
  If the send fails it is retried after 30 s, 60 s, 120 s and so on, ten attempts, then marked abandoned,
  which stays red on the check.
